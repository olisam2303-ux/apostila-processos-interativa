Voltar para a apostila
Ferramentas da Jornada Trello e GitHub para rodar as atividades de Processos na prática

Guia de configuração dos dois sistemas gratuitos que melhor cobrem os assuntos da disciplina — backlog, sprints, Kanban, métricas e, no caso do GitHub, integração contínua de verdade. Cada passo indica em qual semana da apostila ele entra em ação.

Trello — passo a passo GitHub — passo a passo Qual escolher Migrar do Trello pro GitHub

Trello

Gratuito, sem cartão de crédito, e o mais visual dos dois — melhor para turmas que ainda não programam.

1

Criar a conta e o quadro da turma

Em trello.com, crie uma conta gratuita (pode ser com o e-mail escolar). Crie um quadro (Board) chamado, por exemplo, Processos — Turma 1ºA. Convide os alunos como membros do quadro (ou crie um quadro por squad, se a turma for grande).

2
Semanas 1, 2, 6, 7 — Requisitos

Backlog de requisitos

Crie uma lista Backlog. Cada requisito vira um cartão: título no formato "Como um <usuário>, eu quero <funcionalidade> para que <motivo>", critério de aceitação na descrição, e um checklist para os critérios SMART. Use etiquetas (labels) coloridas para marcar RF / RNF, ou Essencial / Importante / Desejável / Adiado (MoSCoW) — a mesma classificação já usada na atividade da Semana 2.

3
Semanas 11, 13, 17 — Sprints

Sprint board e story points

Crie listas Sprint Backlog → Em andamento → Em revisão → Concluído. Ative os Campos personalizados (Power-Up gratuito) e crie um campo numérico "Story Points" — é o que a turma preenche durante o Planning Poker da Semana 11. Ao fim de cada sprint, some os pontos dos cartões que chegaram em Concluído: esse número é a Velocity real da turma (Semana 13).

4
Semana 12 — Papéis do Scrum

PO, Scrum Master e Dev Team

Atribua um aluno como responsável por ordenar o Backlog (PO). Crie uma etiqueta Bloqueado — só quem está no papel de Scrum Master pode remover essa etiqueta de um cartão, depois de resolver o impedimento. Os demais alunos (Dev Team) só movem cartões entre as listas, nunca reordenam o Backlog.

5
Semana 18 — Kanban e WIP

Limite de WIP por coluna

No menu do quadro, ative Limites de lista (gratuito): defina, por exemplo, no máximo 3 cartões na lista "Em andamento". O cabeçalho da lista fica vermelho quando o limite é ultrapassado — é a própria mecânica da Semana 18 acontecendo ao vivo, sem precisar simular com papel.

6
Semana 14 — Retrospectiva

Quadro de retrospectiva

Crie um quadro à parte (ou 4 listas temporárias) chamado Retro — Sprint N com as colunas Liked / Learned / Lacked / Longed for. Cada aluno escreve um cartão por sentimento; ative o Power-Up de Votação (gratuito) para o dot voting dos temas mais importantes a resolver.

Tudo isso funciona no plano Trello Free — nenhum dos Power-Ups citados exige upgrade para uma turma de até ~10 membros por quadro.

GitHub

Gratuito, e o único dos dois que fecha o ciclo até Integração Contínua de verdade — ideal a partir do momento em que a turma já escreve algum código.

1

Criar a conta e o repositório

Em github.com, crie uma conta gratuita. Se os alunos tiverem e-mail escolar, o GitHub Education libera benefícios extras (opcional, não é necessário para nada deste guia). Crie um repositório por squad, ex.: processos-squad-a.

2
Semanas 1, 2, 11 — Requisitos e backlog

Issues como histórias de usuário

Na aba Issues, cada requisito vira uma issue com o título em formato de user story. Crie labels customizadas em Settings → Labels: rf, rnf, must, should, could, wont (MoSCoW) e bug (para as semanas de teste).

3
Semana 18 — Kanban

Project (quadro Kanban nativo)

Na aba Projects do repositório, crie um novo Project em visão de quadro, com colunas Todo → In Progress → Done. Arraste as issues para lá. O contador de itens por coluna, visível no cabeçalho, cumpre o mesmo papel de alerta visual de WIP que o Trello.

4
Semanas 11, 13 — Sprints e métricas

Milestones como Sprints

Em Issues → Milestones, crie Sprint 1, Sprint 2 etc., cada uma com data de entrega. Associe as issues da sprint ao milestone. A barra de progresso do milestone (issues fechadas / total) já funciona como um burndown simplificado para a Semana 13.

5
Semana 20 — Integração Contínua

Primeiro pipeline com GitHub Actions

Crie o arquivo .github/workflows/ci.yml no repositório com o conteúdo abaixo. Ele roda automaticamente a cada envio de código (push), exatamente o conceito de CI apresentado na Semana 20 — a build acontece sozinha, sem ninguém precisar rodar nada manualmente.

name: CI on: [push] jobs: build-e-teste: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Rodar verificação run: echo "Build passou! Aqui entraria o comando de teste real, ex.: pytest ou npm test"

Depois que a turma já tiver algum código com testes automatizados (ex.: de uma disciplina de programação), basta trocar a linha run: pelo comando de teste real.

Tudo isso funciona no plano GitHub Free, inclusive em repositórios privados — não precisa de cartão de crédito nem de upgrade.

Migrando do Trello para o GitHub

Pensado para o momento sugerido acima: fazer a virada na virada do Bimestre 2 para o 3, quando a Semana 20 traz Integração Contínua. Um quadro de turma costuma ter poucas dezenas de cartões — dá pra migrar à mão em uma aula, sem precisar de nenhum script.

1

Antes de tudo: conte e exporte

Anote quantos cartões existem em cada lista do Trello — é a sua conferência de chegada no fim. Depois, no quadro, abra o menu ⋯ no canto superior direito → Mais → Imprimir, exportar e compartilhar → Exportar como JSON. Guarde esse arquivo como backup, mesmo sem usá-lo diretamente — se algo se perder na migração manual, a informação original continua ali.

2

Preparar o "chão" no GitHub antes de mover conteúdo

Recrie no repositório as mesmas labels que existem no Trello (Settings → Labels): as etiquetas RF/RNF/MoSCoW e a etiqueta Bloqueado do papel de Scrum Master. No Project novo, crie um campo numérico Story Points e um campo de status com as mesmas colunas das listas do Trello, na mesma ordem.

3

De onde veio, para onde vai

Cada elemento do Trello tem um equivalente direto — é só uma questão de nomenclatura:

Quadro (Board)→Repositório + Project
Lista (List)→Coluna de status no Project
Cartão (Card)→Issue
Etiqueta (Label)→Label
Checklist→Lista de tarefas markdown: - [ ] item
Campo "Story Points"→Campo numérico personalizado
Membro no cartão→Assignee da issue
Data de entrega→Milestone (Sprint)
4

Migrar cartão por cartão, na ordem certa

Comece pela lista Backlog/A Fazer — geralmente sem histórico, mais rápida de recriar. Para cada cartão: nova Issue com o mesmo título, cole a descrição, recrie o checklist como lista de tarefas, aplique as labels equivalentes, preencha o Story Points e coloque na coluna certa do Project. Deixe os cartões de Concluído por último — servem só de histórico, então podem virar issues já fechadas (Closed) direto, sem passar pelo quadro.

5
opcional, avançado

Acelerar com o GitHub CLI, se a turma já tiver essa familiaridade

Para quem tem conforto técnico: exporte o quadro também como CSV (Power-Up gratuito "Export for Trello" faz isso), instale o GitHub CLI (gh) e crie as issues em lote a partir de uma lista simples de linhas título;labels:

while IFS=';' read -r titulo labels; do gh issue create --title "$titulo" --label "$labels" done < cartoes.csv

Isso não substitui a conferência manual dos campos (Story Points, checklist, coluna) — só poupa o trabalho de digitar título e labels um por um.

6

Conferir e só depois arquivar o Trello

Compare o total de issues criadas com a contagem anotada no passo 1. Não exclua o quadro do Trello de imediato: use Fechar quadro (arquivar, reversível) e mantenha por algumas semanas antes de excluir de vez.

Ideia pedagógica: transforme a própria migração numa atividade de aula, encaixada numa Sprint Review ou Retrospectiva (Semanas 14/17) — "trocar de ferramenta no meio do projeto" é, na prática, o mesmo tipo de mudança discutido na Semana 7 (Gerenciamento de Mudanças em Requisitos). Peça para a turma preencher um Registro de Controle de Mudanças de verdade antes de migrar.
